## Charter v1.4 conflict discovered in PR #46

The former loader opened `dropbear -B` even with empty P26 RAM rescue; it allowed blank-root network SSH. Current `docs/architecture/P25-FOUNDATION-POLICY.ja.md` §§6, 8A require **P25 rescue to be authenticated only**, and P44 absent/corrupt must not expose unauthenticated root. PR #46 now fails closed on absent P26 or missing `/root/.ssh/authorized_keys`; P26-backed rescue uses `dropbear -s` (password logins disabled). No network rescue SSH is expected in the current empty-P26 4号機 environment; UART remains accessible. **This is a security correction, not a G4 network fix.** A separate gate must confirm the authenticated rescue behavior before publication.

BusyBox on the currently running device rejects `ip -d`, `tc -s`, and `ip neigh replace/del`. Replace `ip -d link show` with portable `ip link show`; prefer `arp -s/-d` for the UART recipe.

### Next finite test improvement: tracefs diagnostic

`initramfs/terminal6-g4-trace` provides a **bounded, optional** UART diagnostic. It does not reset network state, update switch registers, change DTB, or write to partitions. When tracefs/net event support exists, it records the first 15-second window around isolated raspi4 ARP/ping traffic, enables `net_dev_queue`, `net_dev_start_xmit`, `net_dev_xmit`, `netif_receive_skb`, `skb:kfree_skb` where available, reports at most the last 120 trace lines, and prints LAN2/eth1 counters before and after. The trace ring is limited to 128KiB/CPU; events and tracing are disabled on exit.

On new unsigned built-in-initramfs P25, the tool is packaged as `/sbin/terminal6-g4-trace`. Run from a known isolated 4号機 **UART shell only**, after confirming raspi4's capture namespace and peer IP:

```sh
/sbin/terminal6-g4-trace
```

When the UART prints `TERMINAL6_G4_TRACE_TRIGGER_PING_FROM_RASPI4_NOW_15_SECONDS`, issue 3 ARP/ping trials from the already isolated raspi4 peer. Capture both sides; parse `net_dev_queue`/ `net_dev_start_xmit` / `net_dev_xmit` to locate the first non-observed stage. `*_UNAVAILABLE` means that tracefs tracepoint did not exist in this kernel, **not** that Ethernet is healthy. Do not declare G4 PASS until normal ARP and bidirectional ICMP succeed on the wire.

A new Image embedding this tool is a different binary and requires fresh G1–G3 hardware acceptance, even if its config and DTB are pinned and offline CI PASS.

### Root cause triage and prohibited shortcuts

Maintain the two distinct possibilities: (1) Linux egress never reaches `lan2` DSA netdev (no TX queue/start-xmit event), or (2) frames reach DSA/master but switch CPU port / tagger / DMA datapath drops them. Simultaneously inspect ingress (port RX but no master RX/IP packets). Do not conclude `noqueue`, DTB CPU-port mapping, SGMII mode, or DMA is broken just because TX counters are zero. Do not silently rewire CPU port 5 to 6, enable a second master or flip PHY mode as a blind fix. Additional source-backed instrumentation and exact trace evidence are prerequisites for an MT7531 driver or DTB corrective patch.

### Upstream MT7531AE vs MT7531BE capability cross-check (source audit)

Upstream Linux `drivers/net/dsa/mt7530.c` `mt7531_setup()` reads `MT7531_TOP_SIG_SR` and derives `priv->p5_sgmii` from `PAD_DUAL_SGMII_EN`. The corresponding `mt7531_mac_port_get_caps()` only accepts SGMII/2500BASE-X on port 5 when `p5_sgmii` is true. **MT7531AE** has SGMII on ports 5 and 6; **MT7531BE** only on port 6, with port 5 RGMII. Reference: https://kernel.googlesource.com/pub/scm/linux/kernel/git/torvalds/linux/+/ac4e04d9e378f5aa826c2406ad7871ae1b6a6fb9/drivers/net/dsa/mt7530.c (mt7531_setup and mt7531_mac_port_get_caps).

The 4号機 FDT presently describes CPU port 5 as `2500base-x` to `eth1`. This requires verifying that the actual switch strap reports port-5 SGMII available and that its PCS is up, not merely that Linux reports a fixed-link 2.5Gbps master. **Do not label the switch BE or change to CPU port 6 without raw switch register/driver proof**. An apparently-up fixed-link is not proof that frames traverse the switch CPU interface.

If netdev tracing shows that frames are actually submitted to `eth1` but not observed on the wire, inspect MT7531 chip variant, P5 SGMII PCS status, actual PMCR/port matrices and MAC TX DMA before changing FDT. If no `net_dev_start_xmit` for lan2, first investigate the software egress path.
