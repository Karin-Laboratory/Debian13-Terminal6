## Minimal source change in this branch

## UART follow-up evidence: confirmed TX counter stall (2026-11-22)

Owner-provided 4号機 UART output (not independently captured raw log) has now established:

- LAN2 PHY carrier and link at **1Gbps/full**, eth1 master at **2.5Gbps/full**.
- `lan2.iflink=24` equals `eth1.ifindex=24`; netdev registration and parent selection succeed.
- `ip route get 192.168.1.2` returns `dev lan2 src 192.168.1.1`; routing is correct.
- BusyBox `arp -i lan2 -s 192.168.1.2 dc:a6:32:01:96:2e` succeeded, showing a **PERM** neighbor. Static entry was deleted after each test. Original neighbor without static ARP was `FAILED`.
- With static neighbor in force, `ping -c 3 -W 2 -I 192.168.1.1 192.168.1.2`: 3 transmitted, 0 received.
- Precisely across this three-Echo test: `Ip.OutRequests 27→30`, `Ip.OutTransmits 27→30`, `Icmp.OutEchos 15→18`; `Ip.OutDiscards=0`, `Ip.OutNoRoutes=0`.
- `/proc/net/dev`: `lan2 RX=10 packets/650 bytes, TX=0`; `eth1 RX=0, TX=0`; link is up and errors reported zero. RX port counters do not demonstrate IP delivery (`Ip.InReceives=0`).
- `tc qdisc show dev lan2`: `noqueue`; `eth1`: `mq` with 16 `fq_codel` children. `noqueue` alone is not evidence of a fault.
- `/proc/net/softnet_stat` does not demonstrate an increasing drop counter in the supplied snapshot.
- Approximately 523s after boot, FE/ADMA/QDMA/WDMA/GMAC register dump and subsequent eth1 link re-establishment; the preceding dmesg had no watchdog/TX timeout message. **Cause of dump unproven**; do not diagnose DMA hang from this alone.

**Interpretation:** Linux IP/ICMP output accounting advances but neither DSA user port nor master TX device accounting advances. IP MIB `OutTransmits` is NOT an Ethernet transmit completion proof. The earliest still-unproven boundary is the packet's actual passage through `dev_queue_xmit`/DSA `ndo_start_xmit` and master driver TX path. Merely changing DTB or qdisc is unjustified.

**Next instrumented kernel gate:** rate-limited/first-N markers for (1) egress netfilter/qdisc/neighbor handoff, (2) DSA user port `ndo_start_xmit`, (3) selected tagger `xmit` result, (4) master eth1 TX driver entry, (5) DMA submission/drop reason. Trace paths against the actual Linux 6.18.63 source/patchset, not guessed symbol names. Successful code execution/CI is distinct from G4 hardware acceptance.

## Charter v1.4 conflict discovered in PR #46

The former loader opened `dropbear -B` even with empty P26 RAM rescue; it allowed blank-root network SSH. Current `docs/architecture/P25-FOUNDATION-POLICY.ja.md` §§6, 8A require **P25 rescue to be authenticated only**, and P44 absent/corrupt must not expose unauthenticated root. PR #46 now fails closed on absent P26 or missing `/root/.ssh/authorized_keys`; P26-backed rescue uses `dropbear -s` (password logins disabled). No network rescue SSH is expected in the current empty-P26 4号機 environment; UART remains accessible. **This is a security correction, not a G4 network fix.** A separate gate must confirm the authenticated rescue behavior before publication.

BusyBox on the currently running device rejects `ip -d`, `tc -s`, and `ip neigh replace/del`. Replace `ip -d link show` with portable `ip link show`; prefer `arp -s/-d` for the UART recipe.
