# C号機 EasyMesh 実装状況（2026-11-15）

## 判定

実装候補は prplMesh 6.0.1（source commit `5ba21ee04a3b34f0d99635eeacd547d78cb67efe`）とする。prplMesh はControllerとAgentの両方、Linux BPL、NL80211 BWLを持つBSD-2-Clause-Patentの実装で、OpenWrt向けにも使われている。C号機のMT7996E/mt76はnl80211を使うため接続方式は合うが、EasyMesh動作互換性はまだ実証されていない。

現時点では**host build、Debian 13 arm64 cross build、事前検査の準備まで**。C号機でIEEE 1905.1 discovery、親子参加、backhaul、端末接続を確認したとは扱わない。C号機への配備・実機起動は未実施。

本作業のWi-Fi Alliance Multi-AP EasyMeshは、別Draft PR #11のIEEE 802.11s/HWMPメッシュとは別プロトコルであり、同一機上の設定や成功判定を共有しない。MLO/6GHz監査PR #10との変更ファイル重複も避けている。

## 参照機Aと既存証拠

- Draft PR #6の読み取り専用A号機比較では、純正Linux 5.4.238、メーカー独自mt_wifi/MT7990 driver/firmware、6GHz AP設定（6075 MHz/320 MHz）が記録されている。観測時点でrax0に接続STAはなかった。これはAの無線状態の記録で、EasyMesh Controllerの稼働証明ではない。
- 本作業セッションではA号機へ接続して追加読取りをしていない。純正EasyMeshの細部は既存の履歴資料にある範囲だけを参照し、未知の設定やプロセス挙動を補っていない。
- `sbat6-easymesh`の2026-08-23/24履歴には、純正T6A Controller (`DeviceRole=1`) とT6B Agent (`DeviceRole=2`)、`MapMode=1`、topology distance 0/1、6GHz backhaul、5+6GHz MLOの成功報告がある。MLO成功報告はAの個体・C号機Debianへそのまま適用できない。
- A上の純正 `mapd`, `p1905_managerd`, `wapp` とOpenWrtのprplMeshは別実装である。純正バイナリ、秘密、設定ダンプをCへコピーしない。

## C号機の既知状態と依存関係

- PR #6の実測ではCのPCIe MT7990 endpoints `14c3:7990/7991` が `mt7996e` にbindし、phy0が2.4/5/6GHz能力を公開した。read-only scanで2.4GHz APが観測され、hostapd 2.12の一時AP起動・TXカウンタ増加を確認したが、外部beacon、client association、DHCPは未確認。
- PR #9はC自身の校正データ取り込みに対するmt7996e初期化修正を記録している。EasyMesh試験はこの修正がCの稼働ソースに含まれ、Wi-Fi初期化が安定していることを前提とする。
- Owner-provided later RC14 results report 2.4/5GHz client association, DHCP and local ping after reboot. Those results prove the baseline AP path at that time, not Multi-AP control sockets or EasyMesh Agent/Controller operation; this session did not access the live unit.
- 6GHzはCのworld regulatory stateで利用不可扱いだった。6GHz/MLO担当PR #6のregdb候補を本ブランチで変更しない。まず2.4/5GHzまでを対象とする。
- Debian上の通常稼働hostapdと、Multi-AP BSS/STA control socketの組合せは未確認。既存のRC14 Wi-Fi成功を壊す設定変更や上書きは行わない。

## 実装上の重要な発見

prplMesh `common/beerocks/scripts/prplmesh_utils.sh.in` はテスト用Linuxプラットフォーム初期化で、dummy WLAN/bridge作成、NetworkManager設定、既存IFのIP flush、bridgeへの移動を行う。この関数をC号機で実行してはならない。C用起動層は既存hostapd/wpa_supplicantとnetdevを利用し、管理IF/IP/route/bridgeを変更しない別実装とする。

prplMesh Linux BPLの現行ソースはLinux側radio indexを0/1の2つに固定している。2.4/5GHzを別々のhostapd制御面として構成できるか、C実機のphy/netdev topologyを確認する必要がある。6GHzを同じ「radio」と見なす推測はしない。

さらにLinux BPLのcredential parserは `wpa2` / `wpa2-psk` 以外をWSC openとして扱う実装になっている。候補パッチはradio interfaceをplatform DBから2系統指定できるようにし、WPA2-PSK、WPA3-SAE、WPA2/WPA3 transitionだけを明示的に受け入れる。未知のsecurity modeはopen扱いせず設定取得自体を失敗させる。6GHzのSAE AKM24は対象外。Cの実際のAP/STA名と認証方式は未取得なので起動ゲートは閉じたままである。

prplMesh `5ba21ee` のLinux NL80211候補ソースはagent-101-vmのGCC 14.2でビルドし、Controller/Agent/IEEE 1905実行ファイルを生成した。上流CTest 14/14 PASS。実行ファイルのELFはx86_64であり、C号機arm64向けではない。隔離DESTDIRにインストールし、Ambiorix共有ライブラリを同梱、RUNPATHを`$ORIGIN/../lib`に限定した。インストール済み4プロセスで開発VMの絶対パスが残らないことと、VM上の依存ライブラリ解決を確認した。C号機向けクロスビルドと実機ABI・起動は未確認。

導入用serviceはopt-in markerがない限り起動せず、上流のLinux `platform_init`を呼ばない。root-ownedのprivate platform DBをruntimeへ0600で原子的に置き、role別にprplMesh control processのみ起動する。既存 `01:80:c2:00:00:13` forwarding ruleがあれば保持し、このservice自身が追加した場合だけ停止時に削除する。Linux BPLが要求する`ebtables`がなければ起動前にfail closedする。preflightは管理IPv4、IF重複、実在netdev/phy、APとSTAのUnix control socket種別、platform DB、WPA設定を読み取り検査する。これは既存AP/STA構成がMulti-AP制御と互換であることをまだ証明しない。

## 受入ゲート

1. Cの現在のhostapd/wpa_supplicant、phy/netdev、管理IFを読み取り採取し、秘密・MACを匿名化する。
2. prplMesh NL80211 BWLをC向けにビルドし、C Debian ABIへ依存ライブラリを合わせる。候補patchは[prplMesh security/interface patch](../../patches/prplmesh/0001-linux-bpl-configurable-radios-and-secure-security-modes.patch)。
3. read-only preflightで既存管理IFと無線制御socketを検証する。
4. 有線管理とAP設定を維持したまま、独立peerを使いControllerまたはAgent一方ずつ試験する。
5. IEEE 1905.1 packet capture、prplMesh topology、backhaul link、実clientのassociation/IP/L2通信を別々に記録する。
6. 切断・復帰、再起動後の復帰を確認してから永続化する。

対向機は、AのController動作が実測確認できるならCをAgentとして使用できる。Aは読み取り専用のままなので、C Controller試験には独立Agent peerが別途必要。プロセス起動や同一機内のloopbackだけでは親子成功としない。

## Debian 13 arm64 cross-build（2026-11-16）

- 固定ソース：prplMesh `5ba21ee04a3b34f0d99635eeacd547d78cb67efe`、PR #12のLinux BPL radio/security patch適用済み。
- Toolchain：Debian cross GCC/G++ 14.2.0 (`aarch64-linux-gnu`)、Debian 13 arm64 rootfsを複製したprivate sysroot。Debian target headers/runtime packagesをその隔離sysrootへ展開し、Ambiorix 8ライブラリを各ソースtagからarm64向けにビルド。ホスト用`amxo-cg`/共有ライブラリとターゲット用Ambiorixを別prefixに分離した。
- Build：NL80211 BWL、Controller/Agent/IEEE 1905 transportを含むCMake/Ninja buildと`DESTDIR` installが完了。全423 build steps完了、ターゲットCTestはクロス実行環境がないため無効化（host側upstream CTest 14/14とproject tests 24/24は別途PASS）。
- 出力ELF監査：73 ELFすべてAArch64 little-endian。依存shared-library名をstageまたはDebian arm64 sysroot内で解決でき、実行ファイルのRUNPATHは`$ORIGIN/../lib`。開発ホストの絶対パスRUNPATHは検出されなかった。ELF監査の全sha/依存情報はowner-private receiptに保存し、バイナリ自体はGitHubへ追加していない。
- 主実行ファイルSHA-256：`beerocks_agent` `80da759623b876e5062801d2eb4af1c5388a29c54feb52cdcd788ac470f48024`; `beerocks_controller` `1c891448adc07d6c8985ffba00b59f3ea097fe1077e45e5434ba98c64389b02f`; `ieee1905_transport` `e0102f38b0d98c636f68f01e683c6728e88b378359df7f7fc4000e268d4c7317`。
- 初回linkでDebian `libevent-dev`のdevelopment symlink先runtime objectがsysrootに欠け、静的archiveへfallbackした。対応する`libevent-2.1-7t64:arm64` runtime packageをprivate sysrootへ追加後、`libamxrt`とprplMesh全体を再buildし成功。target runtime rootfsは変更していない。
- `PRPLMESH_BUILD_TESTS=OFF`であるため、arm64バイナリは生成・静的監査済みだが、arm64実行は未試験。C号機の現在のhostapd/wpa_supplicant socket、radio index/netdev mapping、ebtables、Multi-AP peer、1905 topology、client/data forwardingは未検証。
- 公開再現用のtoolchain fileは`packaging/easymesh/toolchain-debian13-arm64.cmake`。実行には`CUNIT_TARGET_SYSROOT`と、`AMX_HOST_PREFIX`（ホストで実行可能な`amxo-cg`を含むprefix）が必要。ターゲットとホストのAMX prefixを混在させない。
