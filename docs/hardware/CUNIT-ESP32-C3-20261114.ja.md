# 追加解析: ESP32-C3-MINI-1 UART制御

## 実測結論

**DebianのUART1からESP-ATへの照会応答をVERIFIED。** `/dev/ttyS1`、115200 8N1でAT/GMR/CWMODE?/BLEINIT?が全てOK。GPIO reset、ESP firmware更新、Wi-Fi/BLE開始・scan・advertising要求は実施していない。

```text
AT                       -> OK                         0.003 s
AT+GMR                   -> AT version:3.1.0.0-dev
                            (799ebf3 - ESP32C3 - Mar 16 2023 12:58:57)
                            SDK v5.0-541-g885e501d99
                            compile Mar 29 2023 11:52:15
                            Bin version:2.5.0(MINI-1) / OK   0.018 s
AT+CWMODE?               -> +CWMODE:2 / OK             0.005 s
AT+BLEINIT?              -> +BLEINIT:0 / OK            0.005 s
```

ESP32C3/MINI-1の自己申告版表示は、過去資料のESP32-C3-MINI-1と整合する。基板写真による型番刻印の再確認はしていない。CWMODE=2はSoftAPモード設定を示すが、実際の電波・接続可能性は未測定。既存状態を変更していないため「電波が一切出ていない」とは主張しない。BLEINIT=0は照会時点でBLE未初期化。

## UART・DT・GPIO・clock

- ttyS0は管理consoleでMMIO 0x11002000。ttyS1は独立したMMIO 0x11003000、Linux IRQ181、DTのSPI指定0xe9/level。UART2は0x11004000。
- UART1 DTのcompatibleはmediatek,mt6873-uart / mediatek,mt6577-uart。platform側driver=mt6577-uart、serial-base portを経由してttyS1が登録される。
- regにはUART領域0x11003000/0x1000と補助領域0x11036b90/0x20。clock-namesはbaud/bus。参照先は26MHz fixed clockとpericfg_ao系provider。照会前はruntime suspended、openによる通常のUART1 runtime resumeを使用。clock provider設定やparent rateを直接変更していない。
- UART1 DTにはpinctrl-0がなく、pinctrlのowner表示はUNCLAIMED。ただしこれはハードウェアmuxがGPIOモードである証拠ではない。pinsの現値と保持pinctrl sourceではGPIO107/108がmode1のUTXD1/URXD1に対応する。実UART応答も確認済み。今回pinmuxを変更していない。
- GPIO106はpinctrl_parisの236 lines中offset106。現kernelのlegacy base=512なのでglobal618に相当し、**過去のglobal GPIO382をDebianでそのまま使ってはいけない**。character ABIではchip label/offsetで扱う。GPIO106はoutput/highの読み取り表示だが、reset/enable信号を今回toggleして機能実証したわけではない。

UART1のopen ownerは/proc全PIDのfdをst_rdevで調査し0件。ttyS1 gettyはinactive、ESP制御processなし、/proc/consolesにもttyS1なし。照会後のserial counterはttyS1 tx=37/rx=255、Ethernet/SSHとdefault経路を維持。ttyS0の設定は触らず、ttyS1も終了時に元termiosへ復元した。

## 純正経路との照合

GitHubの既存[非公開daemon監査](https://github.com/Karin-Laboratory/SBAT6A-Offline-Archive/blob/main/src/t6a/evidence/VENDOR_DAEMON_AUDIT.md)にもesp32_controllerdとesp32_uartをcompanion制御として記録している。今回さらに所有者保持のC号機2026-10-31 rootfs snapshotのinit scriptとELFの文字列をオフライン確認した。純正バイナリ・スクリプト本文は転載しない。

観測された構造はcontroller CLI→`/tmp/esp32at_fifo`→常駐UART relay→`/dev/ttyS1`。esp32_uartは送受信thread、FIFOとserial openを持つ。controllerには1秒の応答timeout表示がある。snapshotのUART serviceはprocdからrelayを起動し、controller daemonはGPIO reset/enable処理後にecho設定、BLE server/GATT/advertising関連、SoftAP関連のコマンドを扱う。

この起動シーケンスをDebianでそのまま再実行すると、GPIO resetや無線状態変更が入る。そのため純正daemonを起動せず、照会だけを独立実装した。FIFOの内部フレーミングや全コマンドが完全に逆解析済みという主張はしない。今回UART直結でASCII CRLFのESP-AT応答が得られたので、既存relayを経由せずに読み取り制御できることは実証した。

## Linux側APIと実装候補

[esp32-readonly-at.py](../../scripts/esp32-readonly-at.py)は標準Pythonだけの独立実装。ioctl TIOCEXCL、/run lockのflock、既存owner/console検査、115200 8N1、2秒のmonotonic deadline、最大4096 bytes、終端OK/ERROR、異常時の後続要求停止、termios復元を備える。任意ATを許可せず4照会だけをallowlistにする。GPIO・firmware・radio操作APIは実装していない。

stdoutをgateway/開発VMへ回収し、P44へ配置・ログ保存しない例:

```sh
# 既存の安全なSSH transportでstdinをC号機へ渡す。
# ファイルのinstallやcat > /root/...を行わない。
ssh DEVICE 'python3 -B - AT AT+GMR AT+CWMODE? AT+BLEINIT?' \
  < scripts/esp32-readonly-at.py > owner-private-esp32-response.jsonl
```

既存ownerのいない状態でだけ実行する。TIOCEXCLは管理者権限を持つ別processを完全に排除する仕組みではないため、常駐化する場合は管理サービス全体で排他を統一する必要がある。timeoutはローカル待機の終了であり、機器側処理のキャンセルACKではない。toolは曖昧な応答後に要求を重ねない。

## Wi-Fi/BLEとHCIの区別

ESP32-C3のESP-AT機能は[公式Basic](https://docs.espressif.com/projects/esp-at/en/latest/esp32c3/AT_Command_Set/Basic_AT_Commands.html)、[Wi-Fi](https://docs.espressif.com/projects/esp-at/en/latest/esp32c3/AT_Command_Set/Wi-Fi_AT_Commands.html)、[BLE](https://docs.espressif.com/projects/esp-at/en/latest/esp32c3/AT_Command_Set/BLE_AT_Commands.html)のコマンド体系と照合した。ただし実機はvendorの2023年dev buildであり最新ドキュメントの全機能を保証しない。

今回動作しているtransportはASCIIのESP-ATであり、Linux Bluetooth HCI H4/H5ではない。`btattach`を実行しても現在のAT firmwareが標準HCIになるわけではない。BlueZ HCI未登録と、ESP32のBLE AT機能への到達は両立する。ESP32-C3はBLE系でありBluetooth Classic対応を主張しない。別HCI firmware/transportの実現可能性は追加検討で、今回firmware交換は行わない。

今後は、まずeMMC安定化後にこの照会toolを独立したサービスへ組み込み、UART所有権・認証・許可コマンド・応答保護を整える。BLE/Wi-Fiの実通信試験、reset線の物理確認、HCI用firmwareの検討はそれぞれ別の試験範囲とする。
