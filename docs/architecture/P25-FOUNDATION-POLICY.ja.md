# Air Terminal 6 / Debian 13：P25安定基礎の設計憲章

制定：2026-11-18 / 改定：2026-11-18 / 版：1.2 / 対象：SoftBank Air Terminal 6 C号機  
**位置づけ：採用する設計原則の正本。個別P25の実機合格・署名・書込み承認ではない。**

この文書は、P25を何度も作り直す理由と、作り直すべきでない理由を区別するための判断基準である。日々の実装、調査結果、ビルド・実測ステータスは各PRとRunbookに保持する。**新しい実験結果によって、この憲章が自動で変更されることはない。**

## 1. 目的と範囲

Air Terminal 6をDebian 13 arm64の実用ホストとして運用する。第一段階は、再現可能な起動、eMMC/P44の健全性、UART、有線管理LAN、認証付きSSH、復旧経路を確保すること。その後、Wi-Fi AP（適法な6GHzを含む）、Bluetooth、GNSS、WWAN、USB、各種周辺機能を段階的に追加する。

**全ハードウェアの完成は、安定基礎P25の完成条件にしない。** KVMの過去の実証は成果として保持するが、新しい安定版の合格基準を置き換えない。

## 2. 起動・保守の責任分界

| 領域 | 役割と原則 |
| --- | --- |
| **P25（boot_a、32MiB）** | LKに渡すkernel Image・Device Tree・initramfs等を持つブートイメージ。P44を起動・診断できる最小限の基盤とし、更新可能な版として管理する。 |
| **P44（rootfs_data、ext4）** | Debian 13の通常ルートFS。systemd、通常SSH、アプリケーション、firmware、互換性のある追加カーネルモジュールを配置する。 |
| **純正slot B（boot_b/rootfs_b）** | Debianとは独立した復旧経路。勝手に上書き・無効化・失効させない。P25と同じOSの冗長コピーとみなさない。 |
| **P26その他の区画** | 既存の所有個体固有データと起動資産。別途承認・検証された変更以外は触れない。 |
| **外部のraspi4 / UART** | 非依存の管理・ログ・復旧支援経路。ネットワーク故障時の現実的な最後の手段として維持する。 |

この構成は一般的なカーネル／initramfs／rootfsの分離と、検証済み版への復帰という組み込みLinuxの考え方に従う。ただしTerminal 6の非対称A/B構成は製品固有であり、一般的な対称A/B更新方式と混同しない。

## 3. 優先順位と「安定」の定義

1. 所有者が**復旧できる**こと。純正B・UART・保存済み起動資産を優先して保全する。
2. 起動・ストレージの健全性。実証済みeMMCの速度/CQE対策などを、回帰検証付きで採用する。
3. 有線管理LANおよびSSHが確立し、再起動後も復帰すること。
4. P25/P44を再現可能に製造・更新できること。
5. P44で個別機能を継続開発できること。
6. Wi-Fi、USB、GNSS、BT、KVM等の追加機能を充実させること。

上位の要件を損なう下位機能は、本番基礎版へ入れない。**「CIで製造できる」ことは「実機で安定稼働する」ことを意味しない。**

## 4. P25に置く機能の選定原則

- P44を認識・マウント・起動するためのCPU、メモリ、割り込み、UART、必要なclock/reset/pinctrl、eMMC/ext4等を起動経路へ含める。
- 管理ネットワークはP44障害時にも使用できる構成を目指す。LANドライバをすべて `CONFIG_*=y` とすること自体は憲章の条件ではない。**built-in、または同一P25のinitramfsに同梱した互換モジュール**のいずれかで、必要な初期化順序・CPU側RX/TX・ARP・SSHに到達できればよい。
- 純正の構成を無批判にコピーしない。既存OSS、LinuxのドライバAPI、実測された配線・電源・依存関係に基づき、必要最小限で構築する。
- KVMは、サイズ・安全性・保守性と衝突しないなら採用できる任意機能。安定基礎の合格を阻害してまで載せない。
- P25の容量は**32MiB=33,554,432 bytes**である。非圧縮Imageの設計上限（例：35MiB）とは異なる指標としてそれぞれ独立検証する。
- 一度合格したP25を「永久固定」しない。障害、セキュリティ修正、カーネル/Device Treeの不可避な変更に応じ、新版を安全に製造・検証する。

## 5. P44側のモジュール開発と限界

Wi-Fi、BT、GNSS、USB、周辺バス、各種センサー等の**機能実装は原則としてP44側**で進める。ドライバをモジュール化できる場合、必要な共通フレームワークや依存機構はカーネルの構成に先行して持たせてもよい。

ただし、次を必須条件とする。

- `kernel.release`、解決済み`.config`、`Module.symvers`、`System.map`、ソース・パッチ・ツールチェーン情報、同一ビルド由来のモジュールをひとまとまりで保存する。
- モジュールのvermagicだけに依存せず、必要なsymbol/CRC・依存関係・firmwareと、実際のロード／動作を別途検証する。
- Linuxカーネルは**任意の版間で安定した内部モジュールABIを保証しない**。新しいP25カーネルには対応モジュールの再製造・配布・移行が必要になる。
- Device Treeに必要なcontroller、電源、clock、reset、pinctrl等の情報が欠ければ、P44へ`.ko`を置くだけでは解決しない。Overlayの適用可能性もハード固有に検証する。
- 配線・部品・電源が不明なDTノードを想像で有効化しない。未解明機能は`FOUNDATION_ONLY`または`BLOCKED`として扱い、必要なら将来P25を更新する。

目的は「今後一度もP25を作らない」ではなく、**P25を変更する必要がある場合を明確にし、低リスクかつ再現可能に更新できること**である。

## 6. 初回セットアップ・管理SSHと認証

### 公開配布版の初回セットアップ：所有者決定（2026-11-18）

**純正OpenWrt型の初回無認証SSHを採用する。** 公開P25は共通パスワード、配布者の秘密鍵、配布者の個人公開鍵、共有ホスト秘密鍵を含まない。物理的に隔離された有線管理ポートのみで、未設定時は `192.168.1.1/24`、TCP/22 に対して `ssh root@192.168.1.1` を**パスワード・ユーザー公開鍵なし**で受け付ける。この初期無認証アクセスはセキュリティ上の例外であり、通常運用の推奨認証ではない。

- P44が**空**なら、最初のSSHはDebianではなく**P25/initramfsのセットアップシェル**となる。Debian rootfsのP44への取得・展開・検証・再起動の手順は別途実装・実機検証する。P25だけを焼いてもDebian 13は自動的にP44に現れない。
- `passwd root` や `authorized_keys` は**展開済みのDebian P44に対して永続化**しなければならない。initramfs上で単に `passwd root` を実行してRAMの `/etc/shadow` だけを変更しても完了と扱わない。専用初期設定コマンドまたはP44への明示的chroot等で永続設定する。
- rootパスワード設定または有効な公開鍵登録のどちらかが完了し、P44上への保存・読み戻しと再接続が検証できた時点で、**無認証SSH経路を不可逆な再起動を要求せず閉じる**（既存管理セッションを不意に遮断しない）。管理を失う危険がある場合は閉鎖を保留してUARTで診断する。設定状態はP44の適切な永続領域に記録し、電源断・再起動でも復帰しない。
- 認証確立後は通常のDebian P44 SSH（TCP/22）で、設定した個別パスワードまたはユーザー公開鍵を用いて認証する。**公開鍵登録だけの場合は、空パスワード経路を必ず禁止する**。無認証セットアップが一度完了した端末で、P44や通常サービスの故障を理由に無認証rootアクセスを再開しない。
- 初回セットアップ時にも、端末自身が新たなSSH**ホスト鍵**を生成する。秘密鍵はP25公開イメージに埋め込まず、P44の永続状態へ安全に保存・再利用し、P44へのDebian導入で消えないようにする。通常SSHと救援SSHで別のホスト鍵を採用する場合は明記する。UARTなどで指紋を確認できるようにする。初回接続のhost-key確認は必要になり得る。
- 初期無認証SSHは**物理的な直結・隔離LANを必須**とし、WAN、Wi-Fi、家庭LAN、他ポートへのbridge、NAT、転送、DHCPサーバーの自動起動をしない。機器だけで物理隔離の真偽を保証できないため、利用者向け手順で直結を必須条件として明示する。既存家庭LAN `192.168.0.0/22` は `192.168.1.0/24` と重複するため、直接混在させない。
- 初期無認証SSHにより**同じリンクへ先に接続した第三者もrootになれる**。暗号化されたSSH通信であっても、初期利用者の正当性は認証できない。このリスクを隠さない。

### 通常運用と故障時

- 平常時はP44上のSSHを用い、空パスワード・無認証ログインを許可しない。
- initramfsの別系統の救援SSH（候補：TCP/2222）は初回セットアップの無認証TCP/22と区別する。初期設定後の救援アクセスは個別の安全な認証に限り、鍵・アクセス制御がない場合はfail-closedとする。
- `switch_root`後にP44ネットワークが故障した場合は、通常のinitramfs SSHが終了している可能性がある。救援サービス／UART／純正Bなど、故障モードごとに確認する。
- **この節は目標仕様であり、現行のPR #25の公開鍵必須候補に実装されたことを意味しない。** 新仕様には独立した実装、ビルド、初回認証・無認証停止試験、正確なunsigned SHAでの新たな署名承認が必要。

[初回無認証SSHの所有者判断記録](decisions/CUNIT-FIRSTBOOT-SSH-OPENWRT-STYLE-20261118.ja.md)に選択理由、代案、必要試験を記録する。

## 7. 実測・製造・署名・受入を分離する

| ゲート | 完了を意味する証拠 |
| --- | --- |
| 設計確定 | 根拠付きKconfig・DTB・起動依存・P25/P44分担 |
| ホスト製造 | native ARM64 build、署名なしP25実体、サイズ・構造・全量SHA照合、同一ビルドmodule一式 |
| 非公開保全 | 製造入力・実バイナリ・ハッシュ・署名に必要なreceipt・対応モジュールの保存と独立読み戻し |
| 所有者署名 | **当該unsigned P25の完全SHAに対する個別承認**、署名済み実物の独立照合 |
| 実機起動 | 対象個体・slot・カーネル・P44マウント・UART・eMMCの実測 |
| 管理・初期設定受入 | LAN carrierだけでなくARP・双方向IP、P44空状態の隔離初回無認証SSH、端末別ホスト鍵の永続性、P44導入後の資格情報保存、認証成立と無認証経路の停止、通常SSH・救援SSHをそれぞれ実測 |
| 継続性・復旧 | warm/cold boot、障害時のUART/純正B復帰、rollback、rootfs/モジュール互換性と保全 |

各ゲートは`PASS` / `FAIL` / `BLOCKED` / `NOT_TESTED`で記録する。公開CIの製造成功、過去のprivate P25の実機成功、別機体の成果を新候補の実機合格に読み替えない。署名・書込み・slot切替・実機再起動は個別承認とランブックの安全ゲートに従う。

## 8. 更新設計・復旧設計

- kernel/DTB/initramfsと対応するP44モジュールを**互換性のある一組のリリース**として管理する。更新途中の不一致を想定し、失敗時に復帰できる設計を先に用意する。
- 変更前に、対象PARTNAME、容量、元イメージ、署名/ハッシュ、保存先、復旧経路、想定停電点を確認する。
- 原則として純正slot Bと既存の良好な起動資産を破壊しない。slot成功フラグ・試行回数・自動復帰の挙動は実測し、自動フェイルオーバーを推測で保証しない。
- カスタムP25カーネルはDebianの通常パッケージ更新だけでは保守できない。上流セキュリティ修正を定期的に評価し、必要なら新版を製造・検証する。
- 保存していない署名済み版やrollback不能な構成を「安定」と呼ばない。

## 8A. 公開リリースの配布単位とP44導入パッケージ（所有者決定：2026-11-18）

**公開Debian 13リリースの基本単位は、互換性を検証した「署名済みP25起動イメージ ＋ P44導入パッケージ」のペアとする。** OpenWrtのP25/P26ペアに相当するが、DebianではP26を入替対象とせず、P44へDebian rootfsをインストールする。配布名は説明上 `P25-signed.img` と `P44-install.zip` を用いる。実ファイル名・ZIP以外の輸送形式は製造Runbookで決めてよい。

1. **互換性を検証したペアを公開する。** カーネル・DTB・initramfs・P44 rootfs・同一ビルドのモジュール・必要なfirmware/設定の関係を、リリースIDとマニフェストで固定する。正確なP25イメージSHA-256、P44パッケージおよび内部rootfs/モジュールのSHA-256、`kernel.release`、モジュールABI、対象ハードウェア・初期化条件、公開可能な出自と検証状況を記録する。互換性を実証していない組合せを「対応ペア」と表示しない。
2. **`P44-install.zip` は導入用の容器であり、直接ZIP展開するrootfsではない。** Debian rootfs本体は `tar.zst` 等、uid/gid、ファイルモード、シンボリックリンク、必要な拡張属性やファイル能力を適切に保全・復元できるLinux向け形式で格納する。対応モジュール、マニフェスト、導入手順も同梱できる。ZIP内ファイルの順序・形式に依存せず、導入ツールが検証してからP44へ展開する。
3. **初回インストールと既存P44の更新を分離する。** P44が空のext4であることを安全に確認できる場合に限って、初回導入処理を実施する。既存Debian・ユーザーデータ・鍵・設定が見つかる場合は自動上書き・初期化を拒否する。通常の保守はAPT、対応モジュールの更新などを用い、OS丸ごと更新はバックアップ・設定/鍵の保全・ロールバック手段を別途設計・検証する。P44が単一のrootfs領域であることを踏まえ、更新時に上書きしても安全とはみなさない。
4. **検証と真正性を分ける。** 配布ZIPはマニフェスト記載のハッシュと内部実物を独立検証する。単なるハッシュ一覧を配布者認証の代替にせず、公開リリースの真正性を確認できる署名付きマニフェスト等を別途設計する。P25のハードウェア署名・一般ユーザーへの再配布権限や導入条件も独立して確認し、適法・実行可能な配布経路が未成立なら「署名済みP25を一般配布可能」と断定しない。
5. **P44が空の初回動作を整合させる。** [§6](#6-初回セットアップ管理sshと認証)の隔離有線LAN上のセットアップSSHはP25/initramfs側で提供し、P44パッケージの受け渡し・検証・展開・途中失敗からの再試行・Debian側root認証確立・個別ホスト鍵の永続化までの導入工程を別途実装する。`passwd root` のRAM上だけの変更や、P44へのデータ未保存で初回完了を宣言しない。
6. **ペア製造と動作受入は別のゲート。** P25とP44パッケージの製造・保全・ハッシュPASSだけで、署名、LK起動、P44展開、Debian起動、LAN/SSH、初回認証切替、再起動後の復帰までPASSとしない。これらは署名・実機操作の個別承認に従い、順に検証する。

この決定は**配布仕様の設計原則**であり、P25/P44の新規製造、署名、書込み、slot切替、再起動、既存P44変更を許可するものではない。

## 9. 規制・公開範囲

既存OSSを優先し、各ソースの出自・再配布権を確認する。純正バイナリ、個体固有のcalibration/EEPROM、秘密鍵、SIM・認証情報、生ダンプは公開しない。必要なprivate原本は権限を限定して保存する。

6GHz/320MHz/MLO等の無線機能は、機器の認証・国内法令・有効regdb・試験環境をそれぞれ確認するまで送信実験をしない。機能広告やKconfig有効化を適法なRF試験の許可としない。

## 10. 憲章変更の手続き

本憲章は**判断基準**、PR/Runbookは**実装・測定記録**である。CodexやChatGPTは新発見だけを理由に憲章の条件を勝手に更新しない。

方針を変える場合は、担当PRに以下を提案し、所有者による明示的な承認を受けてから本憲章を変更する。

1. 現行方針と変更案
2. 新しい証拠・変更の必要性
3. P44側のみで解決できない理由（該当する場合）
4. 既存の起動・管理・安全への影響
5. 代替案・検証計画・rollback方法

採用した判断は関連PRまたは`docs/architecture/decisions/`の記録へ残し、変更理由が追えるようにする。承認のない提案を確定方針として扱わない。
